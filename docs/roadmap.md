# 后续目标与任务

> 2026-10-31。本文是 PerchCore 后续开发的任务入口。已完成实现与验证见 [状态记录](status.md)，当前性能约束见 [性能与限制](performance.md)。下面的未勾选任务均为待做事项。

## 项目目标

把 PerchCore 打磨成能被不同电子书软件可靠复用的高性能嵌入式 SDK，重点提供 EPUB/TXT 处理、中文检索、稳定文本定位和可恢复的导入任务。

完成标准：

- 调用方能仅凭文档和最小示例独立接入 Rust 或 C ABI，不依赖原 App。
- 接口、错误、内存所有权、字符单位和持久化格式有清楚的版本契约。
- 后台解析或索引任务不会因一把全局锁阻塞所有文档操作；资源归属和释放可控。
- 大文件与高并发有明确资源预算，截断、取消和失败对调用方可见。
- 性能有可复现的数据支持，报告真实耗时、吞吐、峰值内存与跨语言传输成本。
- 支持矩阵内的构建、调用和发布产物有自动化验证。

已确认的范围：Rust 核心、C ABI、纯 Dart 绑定、MIT、最小命令行示例；保留既有 crate 名称和 Locator 的 perch 扩展。EPUB/TXT 是主线，PDF 当前负责结构分析。同步合并和卷页几何继续作为可选 Rust 能力。

## 任务顺序

| 阶段 | 目标 | 前置条件 | 完成标志 |
|---|---|---|---|
| M1 | 可复现基线与完整接口契约 | 当前独立 SDK | 能量化现状，调用方能按文档接入 |
| M2 | 独立上下文、生命周期和并发隔离 | M1 契约；确认新 ABI 兼容方式 | 不同上下文互不干扰，长任务不持有全局注册锁 |
| M3 | 大文件输入与内存预算 | M1 基线、M2 资源归属 | 峰值内存与超限行为受预算控制 |
| M4 | 搜索定位、持久化和损坏输入可靠性 | M1 格式契约；结合 M2/M3 实现 | 命中可追溯，产物可恢复，失败可诊断 |
| M5 | 外部接入与可发布 SDK | M1–M4 收口；确认支持与发布范围 | 外部最小客户端能使用带版本的发行产物 |

M4 的样本整理和回归用例可提前开展。任何优化先记录基线，再比较正确性、耗时和内存，不以换实现方式作为验收结果。

## M1：基线与契约

- [ ] **BASE-01：建立可复现样本集。**
  涉及 `examples/data`、测试夹具和基准工具。覆盖 EPUB 2/3、UTF-8/GBK/Big5 TXT、emoji、跨章节和跨分片短语、超长单行，以及 PDF 结构样本。记录生成方式、大小、字符数、编码和内容指纹；使用可再分发或自生成内容。验收：新克隆能重建样本并得到相同内容校验值，正确性样本与性能样本用途明确。

- [ ] **BASE-02：测量完整处理链路。**
  涉及 `perch-import`、`perch-jobs`、`perch-txt`、`perch-index`、`perch-ffi`。分别测登记、打开/解码、精修、正文抽取、建索引、查询、落盘/重开、切片和跨语言调用。输出机器可读结果与测量说明。验收：记录硬件、操作系统、工具链、样本、冷/热缓存条件、重复次数、p50/p90/p99、吞吐和峰值内存；区分首次构建与实际运行耗时。跨平台无法测得的指标明确标注，不填估算值。

- [ ] **API-01：整理完整方法与数据契约。**
  涉及 `perch-ffi`、`include/perch_core.h`、Dart 绑定和 `docs/ffi.md`。逐项列出参数、必填字段、结果、错误码、字符/字节单位、所有权、句柄范围和关闭行为；建立可校验的 JSON Schema 与示例。验收：每个已有公开方法均有文档和可验证样例，C 与 Dart 对相同调用得到一致结果。

- [ ] **API-02：制定版本与兼容策略。**
  覆盖 crate 版本、C ABI、JSON schema、Locator 扩展及 index.bin/text.json。先形成方案，区分新增字段、方法变更和持久化格式升级。验收：能说明旧调用方/旧产物如何检测兼容性、何时重建索引、如何返回不支持的版本；新增规则有旧版本夹具覆盖。

M1 收口后依据数据提出性能预算和回归门槛，确认后再写入验收标准；不直接继承旧 App 的打开时间或搜索指标。

## M2：上下文、并发与生命周期

- [ ] **CTX-01：设计并实现独立上下文。**
  涉及 `perch-ffi` 注册表与各类句柄。提出显式 context/session 的创建、配置和销毁接口，明确句柄归属、资源配额和旧接口适配。验收：同进程两个上下文互不抢占固定配额；跨上下文误用可诊断；销毁一个上下文不破坏另一个；旧接口按确认的兼容方案继续工作。

- [ ] **CTX-02：缩短注册锁持有时间。**
  把文件 I/O、解析和建索引移出全局注册表锁，制定同一对象的 use/close 协调规则。验收：用可控制的长任务证明另一上下文或文档仍可读取；use/close 竞争没有死锁、误关或悬挂；比较并发读取延迟与 M1 基线。

- [ ] **CTX-03：完善取消、进度和异常退出。**
  涉及 `perch-pipeline`、`perch-jobs`、`perch-ffi` 和 Dart worker。明确取消粒度、可观察进度、在途请求和幂等销毁；线程模型和事件传递方式先形成方案。验收：取消不会把半成品标为成功；关闭能等待或取消在途任务；worker 异常退出后的句柄回收/恢复规则可验证，调用方不无限等待。

- [ ] **CTX-04：可配置资源配额。**
  用上下文配置表达文档数量、并行任务、结果上限等资源约束，提供清楚的超限错误。验收：资源能按上下文隔离，配置值与实际行为一致，非法配置被拒绝；默认值依据基线确认后落地。

## M3：大文件与内存

- [ ] **IO-01：完善路径与缓冲区入口。**
  覆盖 `jobs.refine`、`book.open`、`txt.analyze` 等 bytes_hex 路径。优先增加可复用的文件路径入口，再评估借用缓冲区或流式输入；明确长度、所有权与生命周期。验收：正常大文件处理不需要生成整本书的十六进制字符串，返回有上限的结果；旧入口按兼容方案保留或迁移，Rust/C/Dart 同样本结果一致。

- [ ] **TXT-01：评估并实现大 TXT 存储策略。**
  比较分块解码、窗口缓存和文件映射等方案，处理 BOM、显式编码、跨块多字节字符、换行与随机跳转。验收：全文正确性与现有解码一致；Unicode scalar 定位稳定；大文件切片和重开不丢字、不重复；峰值内存满足已确认预算。编码索引和缓存失效规则写入文档。

- [ ] **IDX-01：控制索引构建与加载成本。**
  测量正文与倒排的重复驻留，评估分批抽取、增量构建、正文存储和按需加载。验收：CJK、单字、拉丁短语及跨分片命中不退化；正文与索引一致性校验保留；新旧样本的耗时和峰值内存可比较。

- [ ] **LIMIT-01：统一输入与输出预算。**
  定义文件/章节/解压数据、抽取字符、查询结果和缓存等限制，向调用方区分“完整”“截断”“超限”“取消”。验收：无法在预算内处理的样本得到稳定错误或明确截断结果，不静默报告全书索引完成；部分产物能够清理或重试。

## M4：定位、持久化与可靠性

- [ ] **LOC-01：建立索引文本到源文本的映射。**
  涉及 `perch-jobs::BookText`、章节区间和命中定位。保留归一化前后的对应关系，明确 EPUB href 与 TXT 原解码字符偏移。验收：空白归一化、emoji、中英混排和跨章节样本均能从命中回到正确源文本；旧产物按版本规则读取、降级或重建。

- [ ] **LOC-02：收口上下文重锚契约。**
  整理现有 CFI/上下文算法，提供匹配质量、歧义和失败信息，避免把低置信结果当成精确定位。验收：重复文本、缺失锚点和内容变更都有确定的结果；第二种调用方能够验证命中原文。实际渲染跳转仍由阅读器集成验收。

- [ ] **STORE-01：明确产物恢复与迁移。**
  涉及 PathStore、索引持久化与任务状态。覆盖写入中断、状态/索引损坏、缺失源文件、版本升级和重试；说明产物目录的单拥有者规则。验收：损坏单书不阻断其他书；恢复不把半成品当成功；旧版本夹具可读取或明确触发重建；多进程支持另行决策。

- [ ] **ROBUST-01：损坏输入与性质测试。**
  对 ZIP/XML、TXT 编码、PDF 结构、Locator 和索引文件建立可复现的坏样本、性质测试及 fuzz 入口。验收：字符转换往返、跨分片查询和损坏产物处理符合契约；发现的问题保留最小回归样本；超时或资源限制可观察，不将全部失败归为一个通用错误。

## M5：接入与发布

- [ ] **SDK-01：第二种技术栈的最小客户端。**
  在现有 Rust/C/Dart 示例基础上，优先提议 Swift 或 Kotlin 中一种；覆盖真实样本解析、索引查询、定位和释放。验收：按公开文档和发行产物即可接入，核心调用不依赖 Flutter，也不恢复原 App UI。Swift/Kotlin 的平台运行证据与纯编译证据分开记录。

- [ ] **SDK-02：确认平台支持矩阵。**
  列出 Rust、C ABI 和各绑定在 Linux/macOS/Windows/iOS 上的编译与运行保证；Android/WASM 如有需求再评估。验收：每项支持都有 CI 或设备证据，未验证项明确标记；iOS 真机交付不以 Rust 交叉编译代替 App 链接与调用。

- [ ] **REL-01：形成版本化发行产物。**
  根据支持矩阵准备静态/动态库、C 头文件、绑定、许可证、校验值和接入说明；评估 iOS XCFramework 等平台包装。验收：最小客户端能只用下载产物运行，不需要原仓库构建缓存；发行内容能追溯到源码提交和工具链。

- [ ] **REL-02：发布准备与兼容回归。**
  整理 changelog、升级指南和回滚/重建规则；先验证 Cargo/Dart 包装，再按确认范围发布 GitHub Release、crates.io 或 pub.dev。验收：打包内容完整且无本地路径依赖，支持矩阵和已知限制与实测一致；公开发布前确认版本和渠道。

## 最近一次开发从哪里开始

依次推进 **BASE-01 → BASE-02 → API-01**。完成它们后输出：

1. 可重建的样本集及说明。
2. 当前解析、索引、查询、切片和内存基线。
3. 完整方法/错误/字符与生命周期契约。
4. CTX-01 的兼容方案与需要确认的资源默认值。

这批任务完成前，保持当前实现的兼容性；不要直接替换全局句柄设计或全文存储方案。

## 实施前需要确认的决策

| 决策 | 确认时点 |
|---|---|
| 新 context/session ABI 如何与现有 C 导出和 JSON 方法共存 | API-02 / CTX-01 方案完成后、改接口前 |
| 默认文档/内存/输入限额，以及超限时截断还是报错 | 基线完成后、CTX-04 / LIMIT-01 实施前 |
| TXT 与索引存储方案、持久化格式变更与迁移成本 | TXT-01 / IDX-01 原型测量后、替换旧格式前 |
| 优先接入 Swift 还是 Kotlin；是否加入 Android/WASM | SDK-01 / SDK-02 开始前 |
| 支持平台、性能预算、发布版本与分发渠道 | 基线与平台证据齐备后、公开发布前 |

PDF 正文抽取/渲染、新格式、网络同步服务、DRM、完整排版引擎和应用 UI 暂不加入当前主线；如改变范围，先确认目标，再调整任务依赖。

## 维护方式

任务开始时记录方案与所依赖的契约。完成后勾选任务，在 [状态记录](status.md) 写明提交、实际验证及仍存在的限制；性能结果链接到可复现的数据和环境。仅因代码存在或单个 CI 成功，不把整个阶段标为完成。

测试围绕外部行为、资源生命周期、旧数据兼容和真实失败样本；文档或可逆的小改动只做相应检查。任务涉及重要决策时先提交具体方案供确认，再实施。
