## 环境与复现

AMD Ryzen 5 9500F，6 核/12 线程，约 15.25 GiB 物理内存；CachyOS、Linux 7.3.1 x86_64，CPU governor=performance。Rust 1.99.0 / LLVM 23.1.1，Python 3.14.8，Dart 3.13.5 AOT。输入和产物位于 WD_BLACK SN7100 1TB 的 Btrfs 分区，挂载启用 zstd:1 压缩。

代码基于 `f5fa808` 加当前工作区的 BASE-01/BASE-02 改动。报告保留完整 Git 提交、dirty 标记、测量入口/Cargo.lock 的 SHA-256 和可执行文件/库的 SHA-256；尚未创建包含本批工作的提交。

64 倍样本为约 4.9 万字符 UTF-8、4.2 万字符 GBK、4.4 万字符 Big5、26.2 万字符 cross-shard、144.2 万字符 long-line，以及各 7.4 万字符的两章 EPUB。PDF 保持三页空白结构小样本。准确大小与 SHA-256 以各报告的 corpus 字段为准。

```sh
python3 tools/make_corpus.py --profile performance --scale 64 --output target/corpus-64
python3 tools/bench.py --corpus target/corpus-64 --iterations 30 --warmups 3 --clients rust,ctypes,dart,dart-worker \
  --clean-build --target-dir target/base02/clean-target --scratch-root target/base02/scratch \
  --output target/base02/linux-scale64.json

python3 tools/bench.py --iterations 30 --warmups 3 --clients rust,ctypes,dart,dart-worker \
  --skip-build --target-dir target/base02/clean-target --scratch-root target/base02/scratch \
  --output target/base02/linux-correctness.json

python3 tools/make_corpus.py --profile performance --output target/performance-corpus
python3 tools/bench.py --corpus target/performance-corpus --samples long-line \
  --stages extract,index,query.hit,pipeline,book.open,book.search --iterations 3 --warmups 1 --clients rust,ctypes,dart \
  --skip-build --target-dir target/base02/clean-target --scratch-root target/base02/scratch \
  --output target/base02/linux-truncation.json
```

复跑 clean-build 时请使用另一个空 target-dir；已有目录会被拒绝。样本生成、全内容校验、编译和进程准备不进入操作耗时。系统缓存未驱逐，存在准备和预热访问；产物写入未做 fsync。详细计时边界见 [测量说明](README.md)。

## 代表性结果

以下来自 performance / scale=64；峰值为整个案例进程的 RSS，包含运行时、准备和验证，不等同 SDK 独占内存。耗时单位为毫秒。

| 入口 / 样本 | p50 | p90 | p99 | 峰值 RSS MiB |
|---|---:|---:|---:|---:|
| Rust long-line 建索引 | 30.633 | 30.765 | 31.949 | 14.711 |
| Rust long-line Registered → Ready 管线 | 36.734 | 37.374 | 37.802 | 24.156 |
| Rust long-line 产物重开 | 2.267 | 2.284 | 2.317 | 23.270 |
| Rust EPUB 2 管线 | 1.691 | 1.744 | 1.767 | 4.836 |
| ctypes long-line 全文 txt.analyze | 19.096 | 20.514 | 21.099 | 79.500 |
| ctypes long-line 800 字 txt.slice | 0.0068 | 0.0077 | 0.0084 | 45.969 |
| Dart long-line 全文 analyzeText | 84.367 | 85.459 | 85.828 | 93.391 |
| Dart long-line 800 字 txt.slice | 0.0070 | 0.0072 | 0.0080 | 29.676 |
| Dart worker long-line 800 字 txt.slice | 0.0164 | 0.0185 | 0.0528 | 29.496 |

本次空 Cargo target 的构建步骤共 **14.452 秒**：Rust benchmark 11.655 秒、FFI 库 1.989 秒、Dart pub 0.024 秒、Dart AOT 0.784 秒。依赖下载缓存仍可复用；这个构建时间不计入上述操作延迟，也不代表新机器安装工具链的总耗时。

## 结果指向的后续工作

全文十六进制传输有可观测成本。long-line 的 ctypes txt.analyze 每次请求约 603 万字节、响应约 301 万字节；末尾 800 字 slice 请求 49 字节、响应 1,738 字节。Dart 公共 analyzeText 同样包括十六进制构造和全量 JSON 传输。路径打开、后台索引与窗口读取应继续作为大文件接入方向；此批不改变默认 API 或限额。

重复命中的摘要成本值得单独优化。UTF-8 样本首条「中文」查询返回 1,024 个命中，Rust query.hit p50 为 **36.116 ms**，而同样正文建索引 p50 为 **0.841 ms**。源码中 snippet 的字符→字节换算会从头扫描；FFI book.search 的 limit=20 在完整 search 后才取前 20 条。因此结果上限目前不会限制全部命中计算。后续 IDX-01 的测量应保留该案例，并分别比较摘要定位和查询上限方案。

编码探测也应按入口区分。GBK/Big5 自动探测和解码的 p50 分别约 4.685/3.760 ms；UTF-8 轻量 decode 约 0.022 ms。编码不同、字符数不同，不能直接推出单位字节的通用排名；显式编码路径可在后续 TXT-01 中单独测量。

超限长行有 5,767,170 个字符。Rust extract/index/pipeline 和跨语言 book.open 均报告实际 5,000,000 字符、truncated=true；尾部「终点」查询返回零命中，结果与已抽取范围一致。这证明该 TXT 样本的截断可观察，不能推出 EPUB、取消或所有恶意输入都已受统一预算保护。

## 证据范围

两套主基线共有 388 个通过案例与 11,640 个计时重复；超限集另有 24 个重复。30 次的 nearest-rank p99 为本轮最大值。微小操作受计时器和调度开销影响；线程池的两请求轮包含调度，不能证明 Registry 中短调用重叠或长任务并发隔离。

本次只有 Linux 宿主执行证据，没有设备、冷缓存、功耗、复杂 PDF、deflate EPUB 或任意真实书库数据。多语言 RSS 包含各自运行时及校验文本，不能跨进程相减后当作纯绑定开销。新 CI 已配置跨平台工具冒烟，尚无这批代码的远端执行结果。

这些结果用于建立可复现的起点，不设发布性能承诺或默认资源预算。下一项为 API-01 完整接口契约，随后依据此数据形成并发和大文件方案。
